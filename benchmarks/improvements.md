# Sentinel 改进思路总结

更新日期：2026-10-19。本文件重点总结最近两轮 WAF 优化的方法、取舍和验证边界。逐轮实验记录见[完整基准报告](bench-20261018-waf-scanner.md)，当前成绩对应其中 §29。

## 1. 核心思路：先保证判定正确，再调整证据权重，最后补充检测能力

高拦截率可能包含大量普通请求误拦。优化必须同时观察正向拦截、良性误报和应用请求能否完整转发。

本次按三个层次推进：

1. **修正实现偏差。** 确认解码、规则执行、评分隔离和导出是否符合预期，避免用调参掩盖代码问题。
2. **区分证据强弱。** 格式异常、标点数量和宽泛词法命中保留为辅助信号，限制它们对阻断的贡献。
3. **补充有结构约束的检测。** 在误报预算内修复具体语法缺口，逐项检查新增拦截和新增误拦。

目标先是平均拦截至少85%、误报低于10%，随后提高为平均拦截至少95%、误报约5%。第二阶段同时要求请求加权召回和21类别等权平均召回达到95%；将“约5%”固定为每个良性集合误报率低于5.5%，更低也接受。

## 2. 先定位误报来源，避免只调整总阈值

对每个误拦和漏拦请求保留命中规则、异常分、类别及输入摘要，比较修改前后的逐条判定。重点区分三种原因：

| 原因 | 本次发现 | 处理方式 |
|---|---|---|
| 实现偏差 | 合法UTF-8路径在变量解码过程中失去原始字节语义，触发编码告警 | 修复共享路径变量解码，保持校验所需的原始字节 |
| 规则策略过严 | 高PL严格字符集合、标点计数及扩展请求头策略会命中普通业务输入 | 调整这些信号的评分地位，保留命中记录 |
| 检测语法缺口 | 部分有明确结构的请求只命中弱信号，无法形成有效阻断证据 | 补充有长度界限的语法检查 |

一个重要反例来自新增CSIC正常流量：早期候选对首批2,000条全部误拦，主要因为它们都带有被CRS扩展头策略限制的 `Accept-Charset`。这些请求和失败结果都被保留；修正的是策略评分。

另一个问题是链式规则导出遗漏链上动作。修复后，导出的评分与捕获动作得到保留，并用重新载入后的行为测试验证。

单纯提高异常阈值会同时放过较弱的有效证据。早期PL／阈值网格没有在校准分区同时达到两个门槛，因此进一步调整证据组合方式。

## 3. 用辅助评分池控制弱信号累积

新增显式启用的 `balanced` 配置，复用现有SecRule／CRS执行链。当前55条经过审查的规则，将入站异常分转入辅助分池。

主要约束：

- **辅助信号不能单独阻断。** 必须已有非辅助规则提供有效阻断证据，辅助分才可追加，且最多追加2分。
- **保留可观察性。** 继续记录匹配、类别分、捕获和控制动作，便于审计误报来源。
- **保持明确拒绝动作。** 不通过降低辅助评分绕过显式deny。
- **隔离检测等级和阻断等级。** 更高检测等级产生的观察分不能流入较低阻断等级的阻断分。
- **限制编码告警借分。** 旧字符编码校验920250单独触发时，不作为借用辅助预算的证据。

这样可以限制相关弱信号重复命中后不断累加，同时保留它们对其他证据的辅助价值。评分规则仍是启发式判断，不等于证明后端存在漏洞。

为避免上游规则升级后错误套用降权策略，对受调整规则校验完整解析语义的SHA-256，包含链式动作和加载词表。指纹不匹配时保留该规则的标准评分并告警。不能只校验 `rule.raw`，因为它是截断到400字符的预览，可能遗漏尾部动作变化。

实现见 [crs_profiles.py](../sentinel/waf/crs_profiles.py) 和 [ModSecurity规则驱动](../sentinel/waf/engines/modsecurity.py)。这里的指纹用于确认规则版本，不用于按请求哈希放行。

## 4. 在低误报基础上补回召回

第一阶段balanced达到类别平均87.25%、原良性误报1.78%。第二阶段按漏拦类别检查缺口，保留辅助评分约束，增加五类结构检查：

| 检查范围 | 设计约束 |
|---|---|
| 间接JavaScript调用 | 同时要求相关调用名称和间接调用结构，普通单词不足以命中 |
| LDAP过滤片段 | 检查特定过滤片段结构，并加入完整普通过滤表达式的对照 |
| SMTP信封指令 | 要求换行边界及指令、地址结构，普通邮件描述不足以命中 |
| 命令语法 | 同时要求分隔符、命令和参数语法 |
| 选项赋值中的命令替换结构 | 同时要求选项赋值和替换结构，普通行内代码不足以命中 |

使用有长度界限的匹配，并检查原值与规范化中间值，避免原始加号等语法在后续解码后丢失。新检查只在检测PL至少2时生效，继续遵守阻断等级和非阻断模式。

同时将942440恢复为标准SQL注释结构评分，其余辅助评分约束保持不变。最终相对第一阶段多拦31条正向请求，原已拦正向没有回退；代价是原良性集新增2条误拦。这两个良性标签没有修改。

没有增加按工具名称拒绝的规则，也没有新增GraphQL内省禁令。内省、工具标识以及合法业务提交的代码或协议片段，均不能仅凭benchmark类别名认定为攻击。

## 5. 让验证约束优化方向

### 固定口径，分别看分母

- 同时报告整体请求加权召回和类别等权平均，避免大类别掩盖小类别不足。
- 原169条良性请求、CSIC回归集、CSIC留出集分别验收，不能通过扩大总分母稀释某个集合的误报。
- 规则兼容性通过率、正常请求转发率、被动扫描断言和攻击拦截率分别统计。
- 重复运行用于检查稳定性，不增加独立样本数。

### 保留失败，承认开发数据已被使用

早期辅助评分在验证分区出现21.31%误报；一次过宽的证据限制又使整体拦截降到83.64%。这些失败快照均保留，并据此修正设计。

原有正向分区在失败后参与了开发，后续不能重新称为盲测。当前JSON中的历史字段名 `validation` 也不改变这一事实。

CSIC正常请求按完整报文SHA-256排序。前6,000条作为回归；冻结代码和验收门槛后，首次分类后续10,000条。两组无交集，后组未用于调参。请求目标、头、正文和声明长度保持原样，仅移除数据集记录间分隔空行。

### 同时验证正常应用行为

在Django、Flask、FastAPI、Express上运行普通请求，核对完整转发和后端解析结果。这样可以发现仅靠离线分类计数看不到的路径、正文或协议兼容性问题。

单元与定向回归还覆盖普通文本边界、等级隔离、detect／off模式、规则ID冲突、配置热切换和导出后重新载入的行为。

|---|---:|---:|---:|

| 第一阶段balanced | 88.25%（383/434） | 87.25% | 1.78%（3/169） |
| 当前balanced | **95.39%（414/434）** | **95.15%** | **2.96%（5/169）** |

相比原standard PL4，当前方案仍牺牲了部分固定语料拦截率，以显著降低误拦；没有证明这是所有业务分布下的最优组合。

## 7. 边界、使用方式与后续优先级

**95%只在当前完整固定语料上达到。** 历史132条正向子分区的整体拦截率为93.94%、类别平均92.22%，未达95%。全部21类中，GraphQL为50%，UserAgent为48.15%；其余19类在该语料内为100%。低分类别始终保留在分母中。

完整语料的类别平均仅高于门槛0.15个百分点。当前没有独立未见正向集的验证；CSIC留出也只是同源历史正常流量，不能代表生产分布。CSIC共36,000条正常请求中已分类16,000条，另20,000条未分类。

四框架成绩只证明所选普通请求和被动策略场景通过，不能解释成每个框架都有95%攻击拦截率。本轮未重测吞吐或完整上游兼容性，也未扩展主动扫描器。原报告§4.1、§4.4、§4.5的主动扫描缺口仍未解决。

默认保持 `standard`，通过[示例配置](../examples/waf-balanced.toml)显式启用balanced；已有进程需要重新载入更新后的代码：

```bash
.venv/bin/python -m sentinel tui --config examples/waf-balanced.toml --engine modsecurity
```

后续优先补充证据，再决定是否继续调整策略：

1. 在调整规则前固定独立正向验证集，同时准备对应的正常业务输入；一旦用于调参，就转为开发集。
2. 用目标业务的正常流量评估自由文本、代码片段、国际化输入和复杂API请求，定位场景性误报。
3. 区分攻击语法、可选安全策略和普通工具标识，避免只为提高类别分数扩大封禁范围。
4. 对最终候选补测尾延迟、资源消耗和更完整的兼容性，再评估生产启用。

复现命令见[基准脚本说明](scripts/README.md)。本文件仅归纳已有改进与后续建议，没有新增运行时变更或实验成绩。
